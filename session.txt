§5 请求头（Android 真机 23 键，全部是"字符串"值）
========================================================================

顺序与真机插入序一致：
  Accept, Content-Type, appVersion, osType, osVersion, DeviceId,
  deviceName, cpuModel, logicPixel, physicPixel, isRoot, IMEI,
  androidId, blMac, wifiMac, CustomDeviceId, appInstallTime,
  appUpdateTime, uid, nonce, timeStamp, token, tokenSign

关键口径：
  osType            = "0"（Android）
  appVersion        = 与 UA、headerSign 内版本三者必须一致
  DeviceId          = 32 位 hex 小写、无连字符；UUID 去连字符即可，
                      非 hex 的持久值用 MD5 派生（跨请求稳定）
  logicPixel        = physicPixel / 3，例如 400x805 / 1200x2416
  isRoot            = "0"/"1" 字符串，不是 bool
  IMEI/androidId/blMac/wifiMac/CustomDeviceId = 空串（真机权限受限）
  appInstallTime    = 稳定值；appUpdateTime = install + 26.8 天
  uid/timeStamp     = 数字的字符串形式
  nonce             = 32 位小写 UUID 文本
  tokenSign         = MD5(排序后的 token 参数 + 固定后缀)

iOS 头：**没有真机样本**，当前实现保留 iOS 形态（大写 UUID、bool isRoot、
CustomDeviceId 带后缀、360x640）。不要用 Android 口径去"修正"它，
也不要声称它已验证。

§6 提交体（save/record）：45 键，其中 31 键参与签名
========================================================================

6.1 固定值（真机 7.3.93 抓包）
  sportType   = 1（校园/积分跑；4=户外自由跑，5=室内）
  roomId      = 0（非房间跑；签名只在 sportType=3 时纳入 roomId）
  latitude    = 0.0        ← 不是起点坐标
  longitude   = 0.0
  more        = true
  goalId      = 0
  themeId     = -1
  complete    = 由是否达标决定
  status      = 0
  isUpload    = false
  unauthorized= 0
  useMobilityTools = 0
  faceCheck   = 0
  segmentJson = ""          ← 提交体为空，真实分段在 OBS
  allLocJson  = ""          ← 提交体为空，真实点位在 OBS
  speedPerTenSec  = []      ← 提交体为空数组
  stepsPerTenSec  = []      ← 提交体为空数组

6.2 计算值
  totalTime   = 秒
  totalDis / validDis = **截断**取整（93.90 → 93），不是四舍五入
  speed       = 配速(分/公里) × 1000（Android/iOS 一致）
  avgStepFreq = totalSteps / totalTime × 60，最小 1
  stopTime    = startTime + totalTime×1000 + 1~5s 暂停抖动（uuid 派生，稳定）
  startTime   = 计划起点（可被 0~4s 随机偏移）
  signature / originalSign = 见 §7

6.3 序列化顺序
  真机 UploadFormatEntity 字段声明是字母序，Gson 按声明序输出。
  本工具用 sorted_body_json() 按 key 排序后进信封，保持一致。
  签名与 JSON 文本顺序无关（sign.rs 内部自行排序）。

6.4 JSON 类型
  数字字段不要写成字符串；bool 字段不要写成 "true"。
  goalId 是整数 0（不是 null）。

§7 签名（31 字段，权威参考 neko-re-sources/native/reimpl-rust/sign.rs）
========================================================================

盐：2slhe02lsfiwowlcixisla_sls-_slaor

字段顺序（UploadSignEntity 声明序）：
  sportType, totalTime, totalDis, speed, startTime, stopTime, complete,
  selDistance, unCompleteReason, getPrize, status, uuid, uid, avgStepFreq,
  totalSteps, selectedUnid, calorie, policy, selRunTime, validDis, validTime,
  useMobilityTools, errorCode, geeToken, unauthorized, themeId, faceCheck,
  goalId, address, avgPower, totalAscent
  （sportType=3 时追加 roomId）

取值字符串化：
  String → 原值；null → "null"；bool → "true"/"false"；数字 → to_string

两种拼法：
  originalSign = 31 项按 key **自然序**拼 "k=v&k=v…"（无 MD5、无盐）
  signature    = 同一批项按 key **忽略大小写排序**拼接 + 盐，再 MD5

常见错误：
  - 用 JSON 序列化顺序去签名（错，必须排序）
  - 把 goalId=0 写成 null 或反之（会改签名串）
  - 忘记 roomId 只在 sportType=3 时参与

§8 五点（fivePointJson）
========================================================================

规则：
  isFixed  = 原样透传点位接口（硬点 1 / 普通点 0），不要按模式改写
  isPass   = 按轨迹是否真实经过判定（40m 吸附容差），**禁止全 true 兜底**
  position = 数组下标，0 起
  flag     = 会话起始毫秒时间戳（与 startTime 同源），不是每点时间
  id       = i+1
  外层包装：
    {"useZip":false, "fivePointJson":"[...]", "runAreaId":…,
     "geoFencesJson":"[...]", "freedomShowFence":…}

isPass 实现：track::wire::point_passed()，遍历 track.locations，
用 BD 坐标做平面距离（MET_PER_DEG_LAT/LNG），≤40m 视为经过；
点位只有 glat/glon 时回退用 GCJ。

跑区三件套来源：围栏接口（fetch_geo_fence_with_area）
  runAreaId       = data.runAreaId（缺省 -1）
  geoFencesJson   = data.geoFences 的数组 JSON 字符串
  freedomShowFence= 围栏列表非空
  围栏接口失败时回落缓存/默认值（-1、[]、false），日志会提示"回退缓存"。

========================================================================
§10 坐标系与轨迹生成
========================================================================

坐标：
  - 点位接口/围栏是 BD-09；服务端上传的 gLat/gLng 用 GCJ-02。
  - track.locations 内部存 BD（gLat/gLng 命名沿用历史的 BD），
    输出 OBS 时 wire::bd09_to_gcj02 转一次，**只转一次**。
  - 生活点 lat/lng 固定 -1.0（哨兵）；coorType = "gcj02"。

生成：
  - 5s 主网格（含丢点 10/15s），再按 1s 加密（densify_locations）。
  - 加密 = 相邻点之间插 k-1 个（k=ceil(dt/1.0)）；5s 间隔插 **4 个**，
    不是固定 5 个。位置按弧长 pos(arc) 插值，不是直线。
  - 不插的情况：端点 ptype=-1；dt<=0；|d_arc|<0.25（终点堆叠段）。
  - 累计量（time/dist/steps）线性插值，端点不变 → 总量守恒。
  - count/stepDistance 最后统一由 steps/totalDis 差分重建。
  - 单向路网：crates/route-planner 用 petgraph DiGraph，A* 只走 Outgoing；
    OSM oneway=yes 只加正向边，oneway=-1 只加反向，无标签按双向。
    加密只沿已选路径取弧长，不感知方向，因此不会逆行。

§11 设备档案（geeToken）与电池/传感器
========================================================================

- 电池/传感器参数**不进跑步提交体**，只进 geeToken 的设备档案：
  电池 → bs/br/plu/hea/btv/btc；传感器 → gpa（是否有陀螺仪）。
- 作用：极验/风控的设备可信度与自洽性（电压随电量、跨请求一致、
  模拟器常缺传感器），不是运动分析。
- 原则：像真机、且同一 DeviceId 跨请求稳定；不要每次随机。
- errorCode 默认 -999 + geeToken 空串；走完整极验链时才是 200。
  服务端不强制，**不要伪造 200**（会制造"有 token 无记录"的矛盾）。
- deviceVerify 默认不上报；官方挂在 requestFivePoint.onSuccess 后，
  贸然打开等于自增校验点，缺 upload/originalSign 预登记时不要开。

§13 常见错误清单（症状 → 原因 → 正确做法）
========================================================================

E1  提交 200 但记录判灰/无轨迹
    → OBS 没传或 key 错。检查：只传一个 key、目录用北京时间、
      Put 的 contentType=text/plain、11 键齐全（含 extension_json）。
E2  403（OBS PUT）
    → contentType 与换签时不一致。Put 用 text/plain。
E3  提交 400/参数异常
    → 头里 appVersion/UA/headerSign 三者不一致；或 body 少键。
E4  "签名错误"
    → 31 字段顺序/排序/盐/roomId 条件；goalId null vs 0；
      bool 被写成 "true"；数字被写成字符串。
E5  点位不显示
    → 少报点位（fivePointJson 被裁剪）；或 isPass 全 false。
E6  步频异常（300+ spm）
    → 10s 窗末窗未按时长缩放；step_freq 常量应为 avgDiff=0/
      maxDiff=0/minDiff=1000。
E7  距离对不上
    → totalDis 四舍五入（应截断）；或加密时端点被改写。
E8  时区错（记录日期差一天）
    → 用了 Local；必须 fmt_cst（UTC+8）。
E9  逆向结论与代码冲突
    → 以 neko-re-sources 文档/参考实现为准；仍冲突就标未验证并问用户。
E10 加密重复转换坐标
    → BD→GCJ 只转一次；转两次会出现几十米偏移。
E11 把 Niko源码 当运行副本
    → 它是旧快照（28 键/双 key/position=999），不要在其上继续开发。
E12 提交了本地资料
    → apis.* / .trae / 抓包原文 已 gitignore；不要 git add -A 后不看清单。

  1) 看是哪个 job、哪一步失败（API: /actions/runs/<id>/jobs）
  2) cargo check 失败 → 编译错误（签名/类型/导入）
  3) cargo test 失败 → 先看是否断言过时（协议更新），再怀疑逻辑
  4) 仅 Windows 失败 → 优先怀疑时间/路径/并发类既有用例，
     重跑一次确认是否 flaky，不要立刻改协议代码
  5) 三平台都失败 → 大概率是本次改动引入，回看 diff

14.4 client 仓库
  同样流程；CI 只有 APK（Android 交叉编译 = lib 编译检查）。
  APK 构建失败时看 build 步骤日志，不要只看到 "APK" 红叉就以为协议错。

14.5 commit message 约定
  fix(protocol): …  协议字段/口径修正
  feat(obs): …      OBS 对象/上传
  feat(run-area): … 跑区/围栏
  test(…): …        仅测试
  chore: …          构建/文档
  中文简述，一句话说清"改了什么 + 为什么"。
